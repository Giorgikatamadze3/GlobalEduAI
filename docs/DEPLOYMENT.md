# GitHub და Vercel-ზე გაშვება

გამოქვეყნებული საიტი: **https://globaleduai.vercel.app**. საწყისი კოდი: **https://github.com/Giorgikatamadze3/GlobalEduAI**. Production ანგარიშები ინახება Neon PostgreSQL-ში. GitHub-ის `main` ფილიალი დაკავშირებულია Vercel-ის ავტომატურ განახლებასთან.

ქვემოთ მოცემულია პროექტის ხელახლა გაშვებისა და გარემოს კონფიგურაციის ნაბიჯები.

## სად რა ინახება

| სერვისი | დანიშნულება |
| --- | --- |
| GitHub, კერძო რეპოზიტორია | საწყისი კოდი და ცვლილებების ისტორია |
| Vercel | ვებსაიტი, HTTPS სატესტო ბმული და Express API |
| Neon ან სხვა PostgreSQL სერვისი | მუდმივი ანგარიშები, პროფილები, ფავორიტები და სესიის ჰეშები |
| OpenAI API | სასაუბრო მრჩეველი, როცა გასაღები, წვდომა და კრედიტები ხელმისაწვდომია |

კერძო GitHub რეპოზიტორიას შეიძლება ჰქონდეს საჯაროდ მისაწვდომი ვებსაიტი. კოდის წვდომა და Vercel-ის deployment-ის დაცვა ცალ-ცალკე იმართება. სატესტო ბმულის სხვა ადამიანებისთვის გაზიარებამდე გადაამოწმეთ [Vercel Deployment Protection](https://vercel.com/docs/deployment-protection).

## ლოკალური შემოწმება

პროექტის ძირეულ საქაღალდეში გამოიყენეთ Node.js 24 და შეასრულეთ:

```powershell
npm ci
npm run check
npm test
npm run build
```

`npm run build` ქმნის `public/` საქაღალდეს მხოლოდ დაშვებული HTML/CSS/JavaScript ფაილებით, `assets/` რესურსებით და საჯარო `catalog.json` კატალოგით. ანგარიშების ბაზა, `.env`, სერვერის კოდი და ტესტები ამ საქაღალდეში არ გადადის. `public/` გენერირებული შედეგია; ცვლილებები შეიტანეთ საწყის ფაილებში და ხელახლა ააგეთ.

ლოკალურად `Server/.env` შეიძლება დარჩეს `AUTH_DB_DRIVER=sqlite` და `AUTH_DB_PATH=data/accounts.sqlite`; `npm start` ხსნის საიტსა და API-ს `http://localhost:3000` მისამართზე. ამ გზით შექმნილი ანგარიშები ლოკალურ ფაილში რჩება.

## GitHub-ზე კოდის შენახვა

1. საკუთარ GitHub ანგარიშში შექმენით **Private** რეპოზიტორია და ატვირთეთ პროექტი.
2. ატვირთვამდე გადაამოწმეთ, რომ `.env`, `Server/.env`, SQLite ფაილები, ატვირთული საბუთები და `node_modules/` commit-ში არ არის. `.env.example` შეიცავს მხოლოდ მაგალითებს.
3. პირველ push-ზე Actions განყოფილებაში უნდა გაეშვას `CI`: Node.js 24, `npm ci`, `npm run check`, `npm test`, `npm run build`.
4. წარმატებული შემოწმების შემდეგ ეს რეპოზიტორია დააკავშირეთ Vercel-თან. მიეცით წვდომა მხოლოდ საჭირო რეპოზიტორიაზე.

CI-ს აქვს მხოლოდ `contents: read` უფლება და ტესტებისთვის არ სჭირდება რეალური მონაცემთა ბაზა, OpenAI გასაღები ან deployment-ის ტოკენი. ასინქრონული ავტორიზაციის ტესტები ნამდვილ in-memory SQLite-ს იყენებს Promise ინტერფეისით; PostgreSQL-ის ცალკე ტესტებიც გარე სერვისთან დაუკავშირებლად სრულდება. Workflow-ის საფუძველია [GitHub-ის ოფიციალური Node.js ინსტრუქცია](https://docs.github.com/en/actions/tutorials/build-and-test-code/nodejs).

## მუდმივი ღრუბლის ბაზა

Vercel-ზე ანგარიშებისთვის გამოიყენეთ PostgreSQL. ლოკალური SQLite ფაილის ან `/tmp`-ში შექმნილი ბაზის გამოყენება მუდმივ შენახვად არ გამოდგება: ფუნქციის ინსტანციები იცვლება და ერთი დროებითი ფაილი საერთო ანგარიშების ბაზას ვერ ჩაანაცვლებს. ლოკალური SQLite ფაილი Vercel-ზე არ იტვირთება. [Vercel ფუნქციის ფაილური სისტემის აღწერა](https://vercel.com/docs/functions/runtimes#file-system-support).

1. Neon-ში შექმენით PostgreSQL პროექტი და ბაზა. ბაზის რეგიონი შეძლებისდაგვარად შეუთავსეთ Vercel ფუნქციის რეგიონს.
2. Neon-ის **Connect** ფანჯარაში ჩართეთ **Connection pooling** და აიღეთ ამ ბაზის pooled connection string. მისამართში ჩვეულებრივ ჩანს `-pooler`; შეინარჩუნეთ პროვაიდერის მიერ გაცემული TLS პარამეტრები. [Neon-ის ოფიციალური ინსტრუქცია](https://neon.com/docs/connect/connection-pooling).
3. სტრიქონი შეინახეთ Vercel-ის `DATABASE_URL` საიდუმლო გარემოს ცვლადად. არ ჩაწეროთ ბრაუზერის ფაილებში, GitHub commit-ში ან გასაზიარებელ ეკრანის სურათში.
4. `AUTH_DB_DRIVER` დააყენეთ `postgres`. PostgreSQL მიუწვდომლობისას სხვა ცარიელ SQLite ბაზაზე ავტომატური გადართვა არ ხდება.

სქემის ინიციალიზაციას PostgreSQL საცავი პირველი მომზადებისას ასრულებს. DB მომხმარებელს უნდა შეეძლოს აპლიკაციის ცხრილებისა და ინდექსების შექმნა/გამოყენება. არ გააზიაროთ ამ ბაზის credential-ები საიტის მომხმარებლებთან.

მხოლოდ `AUTH_DB_DRIVER`-ის შეცვლა არსებულ ლოკალურ ანგარიშებს ღრუბელში არ გადაიტანს. ძველი MongoDB-დან ავტომატური მიგრაციაც არ სრულდება.

### არსებული SQLite მომხმარებლების გადატანა

გადატანა ცალკე, აშკარად გაშვებული პროცესია; მანამდე შეინახეთ წყაროს ბაზის სარეზერვო ასლი. პროექტის ძირეულ საქაღალდეში ჯერ გაუშვით მხოლოდ შემოწმება:

```powershell
npm run auth:migrate -- --dry-run --source Server/data/accounts.sqlite
```

ეს რეჟიმი კითხულობს უკვე არსებულ SQLite ფაილს მხოლოდ წაკითხვის რეჟიმში, აჩვენებს მხოლოდ საერთო რაოდენობებს და PostgreSQL-ს არ უკავშირდება. სხვა ფაილის გადასატანად შეცვალეთ `--source` გზა.

როცა დანიშნულების სწორი ბაზა გადამოწმებულია, მისი `DATABASE_URL` შეინახეთ მხოლოდ ლოკალურ `Server/.env` ფაილში ან სერვერის გარემოში და გაუშვით:

```powershell
npm run auth:migrate -- --write --source Server/data/accounts.sqlite
```

`--write` ანგარიშებს PostgreSQL-ში ერთ ტრანზაქციაში აკოპირებს და ინარჩუნებს ID-ებს, პაროლის ჰეშებს, როლებს, თანხმობას, პროფილებსა და ფავორიტებს. აქტიური სესიები არ გადადის: მომხმარებლები ხელახლა უნდა შევიდნენ. არსებული ანგარიშის შესაბამისი ID/ელფოსტა/პაროლის ჰეში/როლი იდენტურია — ჩანაწერი გამოტოვებულია; განსხვავების კონფლიქტისას პროცესი ჩერდება და მონაცემებს არ გადაწერს. ეს ინსტრუქცია მიგრაციას ავტომატურად არ ასრულებს.

## Vercel-ის პროექტის კონფიგურაცია

Vercel-ში აირჩიეთ **Add New → Project**, დააკავშირეთ GitHub რეპოზიტორია და Root Directory დატოვეთ პროექტის ძირეული საქაღალდე. არ აირჩიოთ მხოლოდ `Server/`: frontend, კატალოგი და build სკრიპტი პროექტის ძირშია.

| პარამეტრი | მნიშვნელობა |
| --- | --- |
| Framework | Express |
| Node.js | 24.x |
| Install Command | `npm ci` |
| Build Command | `npm run build` |
| საწყისი Express მოდული | `app.js`, რომელიც ექსპორტზე გასცემს `Server/server.js`-ს |
| სტატიკური ფაილები | build-ით შექმნილი `public/` |

რეპოზიტორიის `vercel.json` აღწერს Express კონფიგურაციას. ეს არის native Express deployment; პროექტი არ უნდა გადაიქცეს მხოლოდ სტატიკურ HTML deployment-ად, რადგან რეგისტრაციასა და AI-ს სერვერის API სჭირდება. Vercel სტატიკურ რესურსებს `public/`-დან ემსახურება; `express.static()`-ზე დაყრდნობა იქ საკმარისი არ არის. [Express on Vercel](https://vercel.com/docs/frameworks/backend/express), [Node.js-ის მხარდაჭერილი ვერსიები](https://vercel.com/docs/functions/runtimes/node-js/node-js-versions).

Project Settings → Environment Variables-ში დაამატეთ:

| ცვლადი | ღირებულება |
| --- | --- |
| `AUTH_DB_DRIVER` | `postgres` |
| `DATABASE_URL` | თქვენი ბაზის pooled PostgreSQL სტრიქონი; საიდუმლო |
| `NODE_ENV` | `production` |
| `OPENAI_API_KEY` | თქვენი OpenAI API გასაღები; სურვილისამებრ, საიდუმლო |
| `OPENAI_MODEL` | `gpt-5.4-mini`, თუ სხვა მხარდაჭერილ მოდელს არ ირჩევთ |

საიდუმლოები შეიყვანეთ მხოლოდ Vercel-ის გარემოს პარამეტრებში. საჯარო პრეფიქსები, როგორიცაა `NEXT_PUBLIC_`, ამ გასაღებებს არ სჭირდება. `AUTH_DB_PATH` ღრუბლის PostgreSQL რეჟიმში საჭირო არ არის. `EMAIL_USER` და `EMAIL_PASS` საჭიროა მხოლოდ ელფოსტის გაგზავნის ცალკე ფუნქციისთვის; რეგისტრაცია და შესვლა მათზე არ არის დამოკიდებული.

მიანიჭეთ ცვლადები იმ გარემოს, რომელსაც ტესტავთ — **Production** ან **Preview**. სატესტო Preview-სთვის გამოიყენეთ ცალკე ბაზა/branch, თუ არ გინდათ სატესტო რეგისტრაციები Production მონაცემებთან აღმოჩნდეს. ცვლადის დამატება უკვე გაშვებულ deployment-ს არ ცვლის; შექმენით ახალი deployment ან გამოიყენეთ Redeploy. [Vercel-ის გარემოს ცვლადები](https://vercel.com/docs/environment-variables).

შემდეგ გაუშვით **Deploy**. build-ის დასრულების შემდეგ Vercel გაძლევთ რეალურ HTTPS მისამართს. `*.vercel.app` ბმულის ზუსტი სახელი deployment-ის შექმნამდე გარანტირებული არ არის.

## გაშვების შემდეგ შემოწმება

1. გახსენით მთავარი გვერდი და უნივერსიტეტების კატალოგი. ღრუბელში სრული კატალოგი იტვირთება სტატიკური `/catalog.json` მისამართიდან.
2. გახსენით `/api/auth/status`: წარმატებული კონფიგურაცია აბრუნებს `provider:"postgres"` და `ready:true`, ბაზის მისამართისა და credential-ების გარეშე.
3. შექმენით სატესტო სტუდენტი, შეცვალეთ საკუთარი პროფილი/ფავორიტები, გამოდით და ხელახლა შედით. ახალი deployment-ის შემდეგ იგივე ანგარიში და მონაცემები უნდა შენარჩუნდეს.
4. შექმენით სატესტო მრჩეველი: მისი `verificationStatus` უნდა იყოს `pending`; სტუდენტის API-ზე სხვა როლით წვდომა უარყოფილია.
5. HTTPS-ზე `globaledu_session` cookie-ს უნდა ჰქონდეს `HttpOnly`, `SameSite=Lax`, `Secure`, `Path=/`. სერვერმა HTTPS პროტოკოლი Vercel-ის სანდო proxy-ს გავლით უნდა ამოიცნოს, რათა იმავე საიტის Origin სწორად შემოწმდეს.
6. გახსენით AI ჩატი. `/api/advisor-agent/status`-ის `enabled:true` მხოლოდ გასაღების კონფიგურაციას აღნიშნავს. სრული მუშაობა დასტურდება წარმატებული რეალური კითხვით.

რეგისტრაციისა და ჩატის ლიმიტები ამ ეტაპზე ფუნქციის მეხსიერებაშია; რამდენიმე ინსტანციაზე ისინი საერთო გლობალური კვოტა არ არის. ავტორიზაციის პროფილები და სესიები PostgreSQL-ში ინახება. უფრო დიდი საჯარო ტრაფიკისთვის ცენტრალიზებული ლიმიტი ცალკე გასაფართოებელია.

## AI ბილინგის მიმდინარე შეზღუდვა

ბოლო რეალურ შემოწმებაზე OpenAI-მ დააბრუნა `credit_balance_exhausted` / `insufficient_quota`. გასაღების ღრუბელში დამატება ამ ფინანსურ შეზღუდვას არ ხსნის. შესაბამის OpenAI API პროექტში საჭიროა კრედიტებისა და ხარჯვის ლიმიტების შემოწმება; ავტომატური გადახდა ან ბალანსის შევსება ამ პროექტს არ შეუსრულებია.

ასეთი პასუხი საიტზე გადადის უსაფრთხო `503 AI_QUOTA_UNAVAILABLE` შეცდომად, საიდუმლოსა და provider-ის სრული შეტყობინების გარეშე. არ ხდება ავტომატური ფასიანი განმეორებითი ცდა. კატალოგი, ფილტრები, ქულების გამოთვლა და რეგისტრაცია AI ბილინგისგან დამოუკიდებლად მუშაობს. დეტალები მოცემულია [AI მრჩეველის დოკუმენტაციაში](AI-ADVISOR.md).
