# პაკეტები, გამოწერები და ბიზნესის მართვა

მომხმარებლის 40 დავალების განხორციელება. ძირითადი გვერდები: `/#billing`, პროფილის პაკეტის ბლოკი და ადმინისტრატორის `/#business`.

| პაკეტი | თვე | წელი | AI პასუხი / თვე | ფავორიტი | PDF | კონსულტაციის მოთხოვნა / თვე |

| Free | 0 GEL | 0 GEL | 5 | 20 | არა | 0 |

AI/კონსულტაციის ლიმიტები საწყისი პროდუქტის პარამეტრებია და ადმინისტრატორს მათი შეცვლა შეუძლია. წლიური ფასი 12 თვეა, ფასდაკლების გარეშე. წლიურ პაკეტზეც მოხმარების ლიმიტები ყოველ კალენდარულ თვეში, UTC-ით ნულდება. ფასი ბაზაში ინახება თეთრებში: `1900 = 19 GEL`.

პროგრამების აღმოჩენა, არსებული შესაბამისობის შეფასება და ადგილობრივი სასწავლო გეგმა ყველა პაკეტში შედის. ფასიანი ფუნქციებია გაზრდილი AI ლიმიტი, PDF და კონსულტაციის მოთხოვნები. კონსულტაციის მოთხოვნა შეხვედრის დაჯავშნას ან ჩატარებას არ ნიშნავს: დროს ადმინისტრატორი ადასტურებს. Free-ზეც აუცილებელია ანგარიში AI მოხმარების დასათვლელად. AI კრედიტი ნიშნავს ერთ წარმატებულ პასუხს; პროვაიდერის შეცდომისას ლიმიტი ბრუნდება. ეს არ არის OpenAI ანგარიშის თანხის ან ტოკენების ბალანსი.

## ფინანსური და წვდომის წესები

- ბრაუზერი ფასს ან პაკეტის უფლებებს ვერ გასცემს. Redirect გადახდის დამადასტურებელი არ არის. RSA ხელმოწერა მოწმდება JSON-ის წაკითხვამდე, შემდეგ სტატუსი ბანკის receipt-იდან იკითხება.
- ერთი გადახდის განმეორებული callback ვადას მეორედ არ ამატებს. დროებით დაკარგული ბანკის პასუხი რჩება pending; იმავე ინვოისის გაგრძელება იმავე ბანკის idempotency key-ს იყენებს.
- იმავე პაკეტის გაგრძელება არსებულ გადახდილ ვადას ემატება. სხვა პაკეტზე გადასვლა იწყებს ახალ პერიოდს; დარჩენილი დღეების პროპორციული ფასის გადათვლა ამ ვერსიაში არ ხდება. პირობა ჩანს შეძენის წინ.
- გაუქმება აჩერებს შემდეგ ავტოგანახლებას. უკვე დაწყებული საბანკო ოპერაცია შეიძლება დასრულდეს; საჭიროებისას თანხის დაბრუნება ცალკე მუშავდება. შემდგომი renewal callback გაუქმებულ ავტოგანახლებას ვეღარ ჩართავს.
- საბანკო ბარათის ნომერი/CVV ჩვენს ბაზაში არ ინახება. ინახება ბანკის order ID. ავტოგანახლება იყენებს თავდაპირველად დამახსოვრებული ბარათის order ID-ს; ინვოისის ფასი თუ შეიცვალა, ავტომატური ჩამოჭრა არ სრულდება და საჭიროა ახალი checkout/თანხმობა.
- Refund API-ის მიღებული პასუხი საბოლოო დაბრუნება არ არის. თანხა/ისტორია იცვლება ბანკის დადასტურებისას. სრული დაბრუნება მოქმედ წვდომას აუქმებს მხოლოდ მაშინ, თუ ის მიმდინარე პაკეტის ბოლო გააქტიურების გადახდაა; ძველი გადახდის დაბრუნება ახალ პაკეტს არ აუქმებს. ნაწილობრივი დაბრუნება წვდომას ტოვებს.
- შემოსავლები არის რეალური წარმატებული გადახდების GEL თანხა, ბანკის საკომისიოსა და გადასახადების გამოკლებამდე. წლიური ინვოისი სრულად მიღებულ თანხაში ითვლება; ეს არ არის ბუღალტრული პერიოდული revenue recognition.
- აქტივობა იწყება სისტემის ჩართვიდან; წარსული აქტივობა არ არის გამოგონილი. რეგისტრაციის თარიღი არსებული ანგარიშებიდან შენარჩუნებულია. ჩატის შინაარსი და PDF ფაილები ანალიტიკაში არ ინახება.
- PDF გენერაცია მოითხოვს ფასიან პაკეტს და მოწმდება სერვერზე. Vercel-ის მოთხოვნის ლიმიტისთვის მაქსიმუმ 4 MB საერთო PDF გამოიყენება; ფაილები მხოლოდ მოთხოვნის მეხსიერებაში მუშავდება და მუდმივად არ ინახება.

## ბაზა და მიგრაცია

ახალი, მიმატებითი სქემა: `Server/billing-schema.sql`, რვა ცხრილი. ანგარიშის/სესიის ძველი სქემა უცვლელია. ადგილობრივად გამოიყენება ცალკე SQLite; Vercel-ზე — არსებული PostgreSQL. HTTP მოთხოვნები production DDL-ს არ ასრულებს.

1. პირადი პირდაპირი სატესტო კავშირი: `BILLING_TEST_DATABASE_URL` ან არსებული `CONTENT_TEST_DATABASE_URL`.
2. `npm run billing:test-branch`: production-ის ასლზე DDL ორჯერ, რვავე ცხრილის ჩაწერა/წაკითხვა, ledger და usage, ბოლოს სრული ROLLBACK.
3. მხოლოდ წარმატებული ტესტის ზუსტი hash შეიტანება Vercel-ის `BILLING_MIGRATION_TESTED_SHA`-ში. Build-ის `scripts/migrate-billing.js` არსებული სერვერული კავშირით, პირდაპირ endpoint-ზე, ტრანზაქციით ამატებს ცხრილებსა და საწყის პაკეტებს.
4. გამოქვეყნების შემდეგ საჯარო პაკეტების endpoint მოწმდება და ერთჯერადი gate იშლება. განმეორებითი build მის გარეშე მიგრაციას გამოტოვებს.

## ბანკის ჩართვა — ჯერ დარჩენილი გარე წინაპირობა

მომხმარებელმა დაადასტურა, რომ merchant ანგარიში ჯერ არ აქვს. ამიტომ რეალური გადახდები გამორთულია. იმიტირებული გადახდა საჯარო საიტზე ფასიან წვდომას არ გასცემს. პროვაიდერის რეალური sandbox/live end-to-end შემოწმება ვერ შესრულდება merchant მონაცემების გარეშე; ავტომატური ტესტები იყენებს იზოლირებულ mock პროვაიდერს და ნამდვილ RSA შემოწმებას.

მომავალი ჩართვის პარამეტრები მოცემულია `Server/.env.example`-ში. `BOG_CLIENT_SECRET` მხოლოდ server/Vercel secret-ში ინახება. სამუშაო გარემო:

- ადგილობრივი/Preview: ცალკე სატესტო ბაზა, `BOG_ENVIRONMENT=sandbox`, ბანკის sandbox credentials და ხელმისაწვდომი HTTPS `BILLING_PUBLIC_ORIGIN`.
- Production-ში sandbox ჩართვა კოდით დაბლოკილია. Sandbox მონაცემები შემოსავლებში არ უნდა აირიოს.
- ბანკის რეალური ტესტებისა და live merchant-ის მზადყოფნის შემდეგ: `BOG_ENVIRONMENT=live`, `BOG_LIVE_VERIFIED=true`, `BOG_PAYMENTS_ENABLED=true`.
- `BOG_RECURRING_ENABLED=true` მხოლოდ ავტოჩამოჭრაზე ბანკის თანხმობის შემდეგ. მომხმარებლის checkbox ცალკე თანხმობაა; ნაგულისხმევად გამორთულია.
- Callback: `/api/billing/webhook/bog`.
